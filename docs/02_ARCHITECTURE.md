### Key Architectural Characteristics

- **Modular Monolith / Workspace Platform (ADR-082)** — Một deploy, một auth/backend/database/design system; presentation được chia thành `academic`, `organization`, `parent`. Workspace là information architecture, không phải security boundary. `/dashboard` giữ học vụ, `/parish` là dashboard Xứ đoàn, `/parent` giữ Parent Portal. `RootLayout` nhớ workspace gần nhất theo parish+account; desktop sidebar và mobile control sheet chuyển workspace không logout. Backend `roleMiddleware`/tenant checks vẫn là authority.
- **Single-Parish Deployment / Tenant-Scoped Persistence (ADR-106)** — Mỗi production deployment được khóa vào đúng một `DEPLOYMENT_PARISH_ID`; login, public recovery, token issue/verify, seed, backup và background workers không cho client/caller chọn giáo xứ khác. Startup quét động mọi bảng có `parish_id` và từ chối bind HTTP nếu gặp row null/khác scope. Schema vẫn giữ `parish_id`, composite key/FK/query predicate và cache namespace `parishId:userId` như defense-in-depth, restore/import boundary và khả năng test cross-tenant; đây không phải shared multi-parish production runtime.
- **Parish Memory bounded context (ADR-081)** — `/api/parish-profile` sở hữu profile, identity tổ chức, cây đơn vị, nhiệm kỳ, record lịch sử, asset và quan hệ. Cây chuẩn có `BOARD` Ban Điều hành ở root; `BRANCH` Ngành và `COMMITTEE` Ban chuyên môn là hai nhánh song song trực thuộc. Một person có thể có đồng thời nhiều service term; chỉ `position_code` tương thích unit mới tham gia authorization, còn chức danh hiển thị không cấp quyền. Timeline là read model suy ra, không có writer/table riêng. `parish_people.linked_user_id` liên kết account tùy chọn và partial unique index bảo đảm một account không sinh nhiều identity active.
- **Parish Event client boundary (ADR-098)** — `parish_events` tiếp tục do REST/server DB sở hữu. Client chỉ project create/update/delete sau server acknowledgement; cache đọc nằm trong encrypted `dexieStorage` theo `parishId:userId`, không dùng global plaintext localStorage, không tạo mutation cục bộ hoặc delete lạc quan. Store kiểm exact tenant trên response và bỏ kết quả request nếu scope đã đổi. Lịch phụng vụ thuật toán vẫn offline độc lập; durable offline event write là future reassessment cần idempotency receipt.
- **Operational integrity & output boundary (ADR-099)** — attendance, parish-event và native-token mutations commit domain row + redacted audit trong cùng database transaction; ngày nghiệp vụ dùng validator lịch thật thay vì chỉ regex. Undo-import marker và native enable/disable preference đều scope `parishId:userId`; personnel paste import là một admin-only all-or-nothing server command tối đa 100 rows. Mọi HTML print/preview escape dữ liệu user, đi qua Blob URL thay vì `document.write`, tách `window.opener` và sandbox `srcDoc` iframe. Đây là lớp hardening, không thay RBAC/tenant authority hoặc tạo schema mới.
- **Login Gate & Security Envelopes** — **2 cổng đăng nhập UI, chung 1 backend auth (ADR-044/058/087)**: `/login` (chọn cổng) → `/login/phuhuynh` (SĐT + mật khẩu; quên mật khẩu tạo ticket cho Admin, sau đó BGL xác minh qua kênh tin cậy) hoặc `/login/nhan-su` (tên đăng nhập + mật khẩu, liên hệ BGL khi quên). **1 tài khoản = 1 vai trò** (`users.role` enum): đăng nhập sai cổng → role gate logout + chỉ đường sang cổng đúng (GLV kiêm PH dùng 2 tài khoản riêng). Backend dùng `POST /api/auth/login`; credential chỉ lưu bcrypt hash, mật khẩu tạm trả đúng một lần, không có reveal/KBA self-reset. Public ticket trả response generic + bcrypt timing work, rate-limit 5/60s/IP, dedupe một row `(parish_id,user_id)`; chỉ admin cùng tenant thấy inbox và reset atomic sau re-auth.
- **RBAC & Class Scope Guards (ADR-072/089/090/092)** — `roleMiddleware` and `checkUserClassAccess` remain server authority across REST endpoints. Client route/navigation/title state derives from `src/constants/routePolicy.ts`: parent-only `/parent`; staff workspaces `/students|grades|attendance|reports|leave-requests`; `/catechists` là danh bạ staff read-only nhưng ghép thêm management actions chỉ cho admin. `GET /api/students` và `GET /api/students/:id` bắt buộc role `admin|chunhiem|phuta`; phụ huynh bị 403 và chỉ đọc con qua `/api/parents/my-children`. Trong cùng tenant, GLV đọc roster/metadata lớp toàn giáo xứ nhưng không nhận assignment identity; ghi student theo lớp, điểm danh/điểm/thi và controls quản trị vẫn bị chặn theo quyền. `GET /api/classes` chỉ thêm boolean `assignedToCurrentUser` cho GLV; `ExamSessionView` dùng marker này để lọc fail-closed controls/lớp thi về đúng assignment, còn server tiếp tục kiểm `getUserClassIds` cho mọi read/write phiên chấm. Tab quản lý lớp chỉ admin; hidden navigation is not authorization authority.
- **Automatic Viewport Adaptation (`useEffectiveMode`)** — Mobile/tablet shell applies below 1024px; desktop shell begins at ≥1024px on both web and Capacitor. Explicit desktop mode is ignored below the floor and forced-mobile is normalized to desktop above it so JS mode and CSS guard cannot diverge; native runtime is not a separate visibility predicate.
- **Truthful academic mutation acknowledgement (ADR-109)** — Attendance and Grade editors may report success only after either a server response or an encrypted Dexie queue transaction commits. Attendance receipts distinguish `server` from `durable_queue`; grade store promises reject on enqueue failure, matrix dirty IDs remain until acknowledgement, and import does not create success/undo state for a rejected enqueue. The sync engine remains the owner after durable insertion; UI drafts remain the owner before it.
- **Presentation System v4.5 (`App-wide Calm, Confident Parish Product`, ADR-063/065/072/077/078/079/080)** — `src/index.css` là entrypoint duy nhất của ordered graph `src/styles/design-system/00-* → 70-*`; token/cascade ownership được khóa bằng graph contract và production-output comparison. Typed primitives tại `components/common/ui` chuẩn hóa button/form/tab/panel/radio/filter/badge/surface semantics mà không tạo framework hoặc business mapping mới. `PageHeader`, product-view/panel/toolbar/entity/state/auth primitives và desktop/mobile shells tạo một visual grammar dùng chung; ở phone, khối identity/action của `PageHeader` có flex-basis rõ ràng để action không ép hoặc cắt tiêu đề. `DesktopAppShell` dùng `.responsive-page-shell` ở touch/tablet và tier rõ ràng từ desktop 1024px; `embedded-page-section` không sở hữu gutter/max-width lần hai. `PageTransition` + TanStack Router View Transition tạo fade-through ngắn cho pathname change trong vùng content, giữ shell đứng yên; `prefers-reduced-motion` tắt route motion. `lazyWithRetry` cung cấp TanStack-compatible `.preload()`; `useMobileRoutePreload` làm ấm tuần tự primary chunk theo role trong idle time và bottom nav preload theo pointer/focus, nên chunk readiness xảy ra trước fade-through thay vì tạo khoảng đứng trước animation. Browser lifecycle abort/invalid-state/timeout được consume ở `ready`/`finished`, còn `updateCallbackDone` tiếp tục nổi lỗi ứng dụng. `useAccessibleDialog` + `ModalPortal` chuẩn hóa lifecycle/root layering.
  - **Governance:** `lint:ds` v4.5 chạy 8 source rules trên 119 application TSX và hiện có 0 violation. Per-file ratchet giữ ceiling theo file; kết quả static này không tự chứng nhận WCAG hoặc visual conformance.
  - **Runtime evidence:** 5 route bảo vệ đại diện (`/dashboard`, `/students`, `/attendance`, `/grades`, `/finances`), 4 public/auth routes và `ParentForgotPasswordModal` được kiểm ở 1440/390/320 × light/dark: tổng 60 Axe observations và 60 full-page visual/layout captures; thêm một test điều hướng mobile-bottom-nav thật. Protected traversal dùng sidebar trong cùng SPA document, assert canonical URL + `aria-current` + `.product-view`, rồi đợi hết primary loading status trước scan/capture. PNG là evidence artifact, không phải pixel-diff baseline.
  - **Risk-based isolated E2E harness (ADR-093):** Playwright dùng riêng Vite/API 3100/3101, SQLite UUID + owner marker trong OS temp, deterministic synthetic seed, không nạp server `.env`, scrub remote/external DB env, preflight port, chỉ phát `READY` sau Vite/API/seed và cleanup qua reporter. Critical portfolio dùng API-assisted arrange → UI action → API/reload outcome cho auth/session, parent isolation, role boundary, class/student persistence, grade sync, finance ledger, offline attendance, semester lock/promotion denial và Smart Exam server-authoritative finalization. PR chạy tag `@critical`; main/manual chạy full browser/a11y/visual suite; CI fail nếu chỉ pass sau retry. Snapshot 2026-09-01: critical **10/10 PASS** (44,7 giây), full browser **72/72 PASS** (5,4 phút), không skip/retry và sandbox đã cleanup. Chi tiết và non-goals tại `docs/08_E2E_TESTING_STRATEGY.md`. Zoom lock vẫn là explicit WCAG exception; browser E2E không chứng nhận screen reader, physical camera/biometric, OMR field corpus hoặc thiết bị thật.
- **Capacitor Native Shell (ADR-029/088/092)** — Dual-platform: Web PWA và native Android/iOS qua Capacitor 8, appId `com.tnttvn.app`, product label `Catevia`, webDir `dist`. Native production API là `https://tnttvn.onrender.com/api`; dev web proxy `/api` và `/health` tới Hono local. Service worker chỉ đăng ký trên web; native unregister worker/cache PWA cũ. Android fail-closed với `allowBackup=false` cộng backup/data-extraction rules loại toàn bộ app data, chỉ xin `CAMERA` (camera optional vì còn đường tải ảnh) và FileProvider chỉ expose app-specific external files/cache. iOS chỉ khai báo camera, không khai báo microphone vì mọi `getUserMedia` dùng `audio:false`. CI Android hiện tạo debug APK; signed Android release và kiểm thử camera/biometric trên thiết bị thật vẫn là external gate.
- **Web Delivery Security, Release Provenance & Cold Start (ADR-092/100)** — Vercel áp CSP cho HTML tĩnh với `script-src 'self'`, `style-src-attr 'unsafe-inline'` tách khỏi element style, `frame-ancestors 'none'`, `object-src 'none'`, nosniff, referrer và Permissions-Policy `camera=(self), microphone=()`. Theme pre-paint là file `/theme-boot.js`, không còn inline script. Vercel Git auto-deploy bị khóa trong config; build inject meta `catevia-release` đã sanitize, backend `/health` trả public non-secret `releaseId`, và post-deploy gate bắt buộc cả hai bằng exact CI `VERIFIED_SHA`. `/health` được proxy riêng tới Render để System Diagnostics nhận JSON thật; refresh-cookie bootstrap có AbortSignal 65 giây để bao phủ một cửa sổ cold start nhưng không treo vô hạn. Nâng Render always-on vẫn là quyết định vận hành/chi phí ngoài repo. CSP production cũng **không** allow-list nguồn third-party script/style (kể cả Vercel Toolbar `vercel.live`): toolbar chèn `<style>` element nên không thể chạy dưới `style-src 'self'`, vì vậy Toolbar được để **Off cho Production** thay vì nới policy (CSP-TOOLBAR-1, 2026-09-23).
- **Native Biometric App Lock (ADR-085, 2026-08-31)** — `BiometricLockGate` nằm ngoài `RouterProvider`: cold start có preference hợp lệ sẽ không mount protected route cho tới khi native OS xác minh thành công. `@aparajita/capacitor-biometric-auth` 10 dùng LocalAuthentication/BiometricPrompt cho Face ID, Touch ID, Android face/fingerprint; `@capacitor/app` khóa lại khi app chuyển inactive, kiểm tra lại strong-biometry availability rồi tự gọi prompt khi active. Preference chỉ là marker `enabled` scope theo `parishId:userId`; không chứa PII, credential, ảnh hoặc biometric template. Tắt khóa cũng cần biometric; nếu sensor mất enrollment/lockout, recovery duy nhất trong lock screen là xóa marker + logout client state rồi đăng nhập lại bằng mật khẩu. App lock là local privacy barrier, **không phải** server MFA/passkey và không thay JWT/refresh/RBAC/tenant authority. Web/PWA không giả lập biometric lock.
- **Offline Sync Engine (`syncCoordinator` + `useSyncEngine`)** — `syncCoordinator.ts` sở hữu imperative 4-phase push + delta pull; `syncTrigger.ts` là seam không import store/hook để store chỉ phát yêu cầu; React hook chỉ đăng ký runner và sở hữu online/offline/timer lifecycle. Architecture gate cấm store import hook (ADR-105):
  - Store mutation phải hoàn tất ghi operation vào Dexie trước khi gọi `runSyncFlow`; grade/attendance dùng promise chaining để sync engine không đọc queue quá sớm.
  1. **Phase 1 — Compact & Flush**: merge duplicate ops in the queue, then flush batched UPDATEs. Safe compaction rule: `CREATE` + `DELETE` pairs only canceled if `CREATE` is provably unsent local-only (`pending`, `retryCount` 0, no prior error). If `CREATE` may have been sent, keep BOTH `CREATE` and `DELETE` so Phase 1.5 retries the immutable original `CREATE`, remaps Temp ID to Server Real ID, and Phase 3 executes `DELETE` with real ID. Likewise, only an unsent `CREATE` may absorb later UPDATE payloads; once dispatch is possible, later edits remain a separate UPDATE.
  2. **Phase 1.5 — Parent CREATEs first**: student/class/exam CREATEs run before their dependent queue edges; notice CREATE has no dependent edge and runs in the individual phase. All four use a stable `idempotencyKey`, and temp IDs are remapped before a dependent operation can dispatch. Server replay is payload-bound by a one-way normalized create-intent fingerprint (no plaintext payload copy) committed in the CREATE audit transaction, so later legitimate UPDATEs do not change replay identity: the same key plus the same original intent returns the current canonical row; the same key with different intent returns explicit `IDEMPOTENCY_CONFLICT`, never silent success. Rows predating the fingerprint use normalized-row compatibility. A legacy student/class/notice queue row that proves a prior dispatch may recover the canonical ACK and retain its folded local intent as a remapped UPDATE; legacy exam CREATEs similarly extract only the already-supported folded lifecycle/result action before remap. A fresh collision or unsupported mutation fails closed.
  3. **Phase 2 — Group batchable ops**: grade/attendance UPDATEs grouped into batch requests.
  4. **Phase 3 — Individual ops**: student/class/notice/exam CREATE, DELETE and non-UPDATE ops processed one-by-one.
  Then **Pull Delta** (`fetchAllData`) refreshes client state.
  - Conflict handling: LWW field-level merge on version conflict for Grade/Attendance (client edit kept), Server-Wins for Student/Class/Notice/Exam CRUD (with explicit Toast separation). Strict Optimistic Concurrency Control (OCC) version enforcement, exponential backoff. Retry thresholds: server/client errors retry up to 3 (`MAX_RETRIES`), network errors bypass the cap up to 5 attempts. Dexie operations wrapped in atomic `db.transaction`. User isolation enforced fail-closed (`isOwnOp`) with 1-time `migrateLegacyQueueUserIds`.
- **CQRS Read Model Projections** — `ReportingApplicationService` owns authorization, parish policy/date-range resolution and one transaction snapshot. Pure SQL read repositories (`ReportCardProjectionRepository`, `ClassSummaryProjectionRepository`) receive that executor + immutable context and remain separate from write models (4 Drizzle write repositories); architecture tests reject repository → service imports (ADR-104).
- **Official academic output authority (ADR-113)** — Every official report, print and export asks the server Reporting boundary for its authorized class inventory, roster and report-card DTOs. Open years are projected from current server facts; `FINALIZED|PROMOTED|ARCHIVED` years use only the finalization policy and per-student snapshots captured by the lifecycle transaction. Missing legacy class/branch/report evidence is an explicit conflict; client Zustand/Dexie/current settings are never a historical fallback. Academic-year creation is online-only and does not change local selection or show success until the authoritative server row is acknowledged.
- **Current command-boundary profiles (ADR-113)** — Catevia does not claim that every route already follows one uniform Clean Architecture profile. New command paths use a named application service, or an approved route-local command callback whose transaction/idempotency/receipt lifecycle is owned by a dedicated service. Operations uses the latter profile: routes compose resource-specific rules inside `runIdempotentOperationsCommand`; the service owns begin/commit/rollback, receipt hashing and replay. Five explicit `db.transaction` calls in Operations are read-only query snapshots. Direct route calls to `runDbTransaction` are a closed legacy allowlist and cannot grow without an ADR/test update.
- **Fail-Closed Database & Deployment Readiness (ADR-051/106)** — `db/index.ts` vẫn thực thi bootstrap + versioned migrations, nhưng `server/src/index.ts` bắt buộc gọi schema readiness và single-parish data preflight **trước seed, bind HTTP port và background workers**, rồi kiểm lại parish scope sau seed. Gate schema kiểm migration manifest, tenant/data-integrity indexes/triggers, composite PK và `foreign_key_check`; gate deployment khám phá mọi table có `parish_id` và chỉ cho exact configured parish. Bất kỳ partial schema hoặc mixed/null parish data đều làm startup fail-closed; không có auto-rewrite/purge để làm gate xanh.
- **Atomic Finance Command Boundary (ADR-051, 2026-08-21)** — mọi Finance write (`createFund`, `createTransaction`, `deleteTransaction`, `updateStudentFee`) có implementation duy nhất trong `FinanceApplicationService` và chạy qua `runDbTransaction`. `updateStudentFee` tái sử dụng `createTransactionInTx` để payment ledger + audit + fee record dùng cùng transaction, không nested transaction; legacy `financeService.ts` chỉ giữ query/read logic và re-export command để import cũ không bypass ACID boundary.
- **Risk-baseline invariant hardening (ADR-101, 2026-09-03)** — Dexie queue/conflict ownership là exact `(parishId,userId)` và bất biến; row legacy thiếu một trong hai bị quarantine thay vì gán cho phiên đăng nhập mới. Grade override/restore đọc policy version, semester lock, student class và assignment qua cùng write transaction. Finance fee update reconcile một linked receipt thay vì append; batch thu cả lớp là một transaction. Multi-statement migrations bọc `BEGIN IMMEDIATE` và ghi marker trong cùng commit. Notice delete là tombstone; `parent_revoked_at` chỉ cho phép delta gửi redacted eviction khi một notice từng-visible đổi sang staff, không tiết lộ notice nội bộ mới.
- **Durable Notification Worker (ADR-102/111, 2026-09-08)** — `notifications` là queue authority, không còn chỉ là history: enqueue chỉ resolve sau durable INSERT; `delivery_kind`, `attempt_count/max_attempts`, `next_attempt_at` và DB claim lease giữ nguyên dispatch intent và ngăn hai replica cùng dispatch một row. Startup drain, retry wake-up và poll thu hồi lease hết hạn. Audience `target_user_ids` là tenant-scoped SSOT cho Web/native; target JSON hỏng fail-closed thành tập rỗng, provider chưa cấu hình hoặc partial push failure không được đánh dấu `sent`. Telegram đã retire: migration/startup revoke link, consume token và terminalize retrying rows; recovery chỉ materialize `web_push`. Delivery là at-least-once: crash sau provider accept nhưng trước DB acknowledgement vẫn có thể gửi lặp và cần provider-level idempotency/per-recipient receipts nếu yêu cầu nâng cao.
- **Academic Finalization, Policy Read & Local Backup Hardening (ADR-103, 2026-09-04)** — `finalizeYear` đặt terminal/semester-lock guard, completeness checklist, source/policy reads, promotion specification, snapshot upsert, year lock và audit trong cùng `runDbTransaction`; mọi helper nhận cùng executor. Parish policy và academic-year range chỉ fallback khi row/config business vắng hoặc không hợp lệ; lỗi query/infrastructure propagate và rollback decision/write path. Local SQLite backup chỉ publish file sau `VACUUM INTO` vào unique partial artifact rồi atomic rename; checkpoint có thể degraded nhưng `VACUUM INTO` lỗi sẽ fail run, xóa partial, không upload/retention/ghi daily marker và không raw-copy main DB thiếu WAL.
- **Remaining Audit Boundary Hardening (ADR-104/111, 2026-09-08)** — base grade upsert/undo resolve policy version trong write transaction; reporting application service truyền một transaction/policy context xuống projection repositories; retryable batch-promotion callbacks không mutate response state; và `server/src/index.ts` là composition root duy nhất sở hữu signal/shutdown cho HTTP, schedulers, notification delivery, Puppeteer và DB. Telegram lifecycle không còn thuộc runtime.
- **Recovery, Tenant Scheduler & Dependency Seams (ADR-105, amended by ADR-106)** — promotion transition persist target year và có durable reconciliation derived từ snapshot/promotion rows; retry chỉ xử lý item unresolved, archive fail closed. Sunday scheduler giữ marker/recipient tenant-scoped và isolation semantics, nhưng production enumeration nay bị khóa vào deployment parish; multi-parish composition chỉ còn ở dev/test. Remote restore yêu cầu target fingerprint, empty/schema-compatible target, row-count/FK/schema verification. Partial JSON restore fail-closed trước destructive work khi có protected lifecycle hoặc dependency/provenance ngoài profile; purge/restore cùng advance tenant-scoped client-data generation trong transaction để mọi thiết bị reset cache và queue cũ trước sync. Restore UI không nhận uploaded JSON làm read authority và chặn khi own queue chưa settled. Domain policy ports không còn DB/JWT type; adapters bind đúng transaction executor, application services không phụ thuộc HTTP middleware. Client sync cycle và dead GradeAggregate path đã được loại bỏ.
- **Reporting current scope (ADR-010 amendment, 2026-09-05)** — current MVP có đúng hai server CQRS projections: report card và class summary. `ParishSummaryProjection` là deferred candidate, không phải runtime defect; chỉ mở lại sau product contract rõ ràng.
- **Architecture inventory gate** — `npm run lint:architecture-inventory` đếm current Hono route modules, services, repositories, domain modules và Drizzle tables; CI fail nếu các số public trong sơ đồ này drift khỏi source.

## 2. Layer Boundaries & Dependency Rules

| Layer | Can Import From | Cannot Import From |
| :--- | :--- | :--- |
| `pages/` | `components/`, `stores/`, `hooks/`, `utils/`, `lib/` | `server/` |
| `components/` | `stores/`, `hooks/`, `utils/`, `lib/` | `pages/`, `server/` |
| `stores/` | `lib/`, `utils/`, `types/` | `components/`, `pages/`, `hooks/` |
| `hooks/` | `stores/`, `lib/`, `utils/` | `components/`, `pages/` |
| `lib/` | `types/` | `stores/`, `components/`, `pages/`, `hooks/` |
| `utils/` | `types/` | `stores/`, `components/`, `pages/`, `hooks/`, `lib/` |
| `routes/` (server) | `services/`, `middleware/`, `utils/`; `db/` only for approved read composition or ratcheted legacy command boundaries | `client/`; new ad-hoc transaction owners |
| `services/` (server) | `db/`, `utils/`, `repositories/`, pure `domain/` | `routes/`, runtime import từ `middleware/` (trừ auth infrastructure allowlist) |
| `repositories/` (server) | `db/`, pure `domain/`/`utils/`, repository-local type contracts | `routes/`, `middleware/`, `services/` |
| `domain/` (server) | domain siblings, pure utilities, transport-neutral types | `db/`, `middleware/`, `routes/`, `services/`, `repositories/` |

### Command and transaction ownership profiles

1. **Named application-service command (preferred for new or extracted paths):** route validates transport input and delegates; the service owns authorization/policy orchestration and the transaction; repositories accept the passed executor.
2. **Receipt-service command (approved for Operations):** the route-local callback is the application-command composition boundary, while `runIdempotentOperationsCommand` exclusively owns transaction lifecycle, idempotency receipt, replay and commit/rollback. Moving every callback into a class is not required unless a concrete change benefits from extraction.
3. **Legacy direct route transaction (ratcheted):** only the explicit allowlist in `architectureBoundaries.test.ts` may call `runDbTransaction`; no new route/file may join it without current-truth evidence and an ADR amendment.
4. **Query snapshot:** routes may open an explicit read-only transaction when multiple authorization/projection reads need one snapshot. This is not command ownership and must remain mutation-free.

Automated gates protect domain purity, service→HTTP separation, repository→service direction, composition-root lifecycle, store→hook direction, the direct-route transaction allowlist, Operations transaction/receipt delegation and read-snapshot count, Reporting read-only/client-authority rules, and the Parish Events write tombstone. They are targeted structural gates—not proof that every business rule is correctly placed.

## 3. Security Envelope

- **Cross-domain completion (XD-01/XD-07):** promotion approval and membership completion are separate facts; receipt metadata commits with membership and is shared by list/retry/archive reconciliation. Offline parent CREATE ACK remains encrypted on its existing owner-scoped queue row until local remap succeeds. Recovery replays that ACK without a second server CREATE; a failed ACK persistence still retries the original idempotency key. Remap does not depend on a temp row surviving in Zustand, and storage/parse failure aborts the cycle before children. ACK rows are excluded from compaction/pruning. This is local reconciliation recovery, not instant revocation or proof of every browser crash/interleaving.
- **Historical academic boundary (XD-02/XD-03):** year finalization owns concrete policy inputs, original class labels and student cohort/report snapshots in its transaction. Reporting selects that evidence for finalized years; promotion evaluation/approval uses frozen metrics/policy, not current settings. Current identity/authorization and profile visibility stay authoritative. Legacy missing provenance is an explicit conflict, not a current-state backfill. Finance historical reads use persisted fee class/year facts plus evidenced cohort, independently of current student membership. No enrollment-history subsystem or generic projection engine is introduced.

- **Academic projection ownership:** manual daily-entry add/delete và Exam complete ghi ledger/derived Grade trong cùng transaction; `gradeService.upsertGrade` tính lại nguồn `daily_avg` từ ledger kể cả legacy client payload, không lấy local-device average làm authority. Client giữ preview riêng về mặt authority: không enqueue Grade projection, authoritative Grade pull không bị local attempts ghi đè. Explicit manual/override vẫn thắng; generic grade-import undo không revert daily projection độc lập với ledger.
- **Date-keyed lock boundary:** Attendance/Leave writers kiểm canonical calendar period và tất cả persisted year ranges cùng parish chứa date trong cùng write transaction. Đây là protection cho legacy overlapping ranges, không phải migration/reinterpretation lịch sử. New year configuration bị giới hạn trong canonical August–July range.

- **Auth** — JWT HS256 (access 15m, refresh 7d, tách `JWT_SECRET`/`JWT_REFRESH_SECRET` bắt buộc ở production), bcrypt 12 rounds (A-NEW-19, 2026-08-11: upgrade từ 10 theo OWASP, rehash-on-login cho hash legacy cost 10), `tokenVersion` validated on every request (revoked on logout & password reset), `failedAttempts` auto-lock at 5 (atomic SQL increment — A-NEW-19 fix TOCTOU lost update). **Refresh token rotation** (`refresh_tokens` — lưu sha256 hash, rotate mỗi `/refresh`, reuse detection thu hồi toàn bộ phiên khi phát hiện đánh cắp; logout per-session). **A01 Phase 1 (2026-08-10)**: refresh token chuyển sang **HttpOnly cookie** `parish_refresh` (`Secure` ở production, `SameSite=Lax`, `Path=/`, 7 ngày; client `credentials:'include'`; `/refresh` đọc cookie trước, body chỉ là backward-compat). Access token (15m) giờ **memory-only** (A-NEW-10/20, 2026-08-11: không persist localStorage — XSS không lấy được; sau reload bootstrap lại qua `/auth/refresh` cookie HttpOnly). **A01 Phase 2 (2026-08-10)**: XSS sinks đã đóng — `ReportExportService` không còn `document.write` (Blob URL/srcdoc); print popup escape toàn bộ field user; A01 đã đóng P1. **ADR-045 (2026-08-16, amended 2026-09-17)**: session state persist 2 tầng — localStorage `parish_current_user` chỉ chứa **marker không-PII** `{id, role, parishId}` cho bootstrap/UX guard, không làm sync/transport authority; snapshot đầy đủ (username/fullName/phone) **mã hóa AES-256-GCM tại-rest trong IndexedDB** (`parish_auth_user`, dexieStorage, khóa non-extractable, AAD + tenant-scope). Document-local `tenantScope` (`parishId:userId` + revision) owns live-store/queue continuity. `/auth/refresh` trả identity binding `{userId, parishId}` và `/auth/me` trả `parishId`; client từ chối activate/retry/reconcile khi owner đã đổi. Snapshot hỏng/thiếu → rebuild qua `GET /auth/me` khi online (offline → logout sạch); mọi đường session chết dọn cả marker lẫn snapshot (A-NEW-54).
- **Authorization (RBAC)** — 4 roles (`admin`, `chunhiem`, `phuta`, `phuhuynh`); `roleMiddleware` on all routes + `checkUserClassAccess` for class-scoped roles.
- **Tenant Safety Namespace (ADR-031/046/106)** — **Mọi query vẫn phải mang `parish_id`**; read-back không ngoại lệ. Cross-parish read/write bị chặn trước khi check quyền chi tiết (sai parish → 404, không lộ sự tồn tại). Mọi định danh tiếp tục composite hóa, kể cả `users.username` → `UNIQUE(parish_id, username)`. Production login lookup luôn dùng `DEPLOYMENT_PARISH_ID`; legacy body không chọn tenant. Multi-parish regression còn chạy ở dev/test để chứng minh isolation, dù topology production là một parish mỗi deployment.
- **Input validation** — Zod schemas on all endpoints (trim, enums, max lengths); 10MB body limit; batch arrays cap tường minh (SEC-BATCH-CAP-1, 2026-08-24: import rows ≤2000, grades batch ≤2000, attendance records ≤500).
- **QR report-card signing** — HMAC-SHA256 qua `REPORT_HMAC_SECRET` **bắt buộc production** (SEC-HMAC-1, 2026-08-24: fail-closed module-level như JWT_SECRET; verify giữ legacy chain để QR cũ còn xác thực; không còn literal public trong source).
- **Security headers** — CSP, HSTS, X-Frame-Options `DENY`, `nosniff`, Referrer-Policy, Permissions-Policy; CSP violation reports thu tại `POST /api/csp-report` (public, rate-limited — OBS-1, 2026-08-24).
- **Rate limiting** — in-memory Map: 1000 req/60s per IP general, 10 req/60s login (resets on restart; acceptable for single-parish scale).
- **Data safety** — destructive ops (purge/restore) snapshot qua `safetySnapshot.ts` + `blobStorage.ts` (ADR-041). SQLite local dùng `VACUUM INTO` vào partial artifact rồi atomic rename; lệnh lỗi làm backup fail closed, không copy riêng main DB khi WAL có thể còn committed pages (ADR-103). Turso remote dùng read-transaction logical snapshot, checksum SHA-256, gzip + AES-256-GCM và R2 độc lập (`BACKUP_ENCRYPTION_KEY`, ADR-059). Restore remote chỉ vào target cô lập đã migrate: command cần SHA-256 fingerprint xác nhận target, preflight target rỗng + schema/cột tương thích, rồi read-back row counts, `foreign_key_check` và schema readiness; không restore thẳng production (ADR-105). Disk Render là ephemeral nên remote production không được fallback local.

## 3.1 Production delivery authority (ADR-057)

Push `main` không tự deploy. GitHub CI phải hoàn tất secret scan → lint zero-warning/design guard → typecheck → coverage tests → build → Playwright. Chỉ workflow `Production Deployment Gate` sau `workflow_run=success` mới được gọi Vercel và Render bằng đúng immutable SHA, đợi cả hai live và smoke-check. Smoke bắt buộc đối chiếu frontend meta + backend health `releaseId` với `VERIFIED_SHA`, xác nhận unauthenticated `/api/auth/me` trả 401 và kiểm CSP/HSTS. Nếu SHA không còn là HEAD, release lệch, security header thiếu hoặc thiếu production secret, deployment dừng fail-closed.

## 5. Durable Delta Sync and Exam Variant Boundary (ADR-094)

- `GET /api/sync/watermark` establishes a server-clock snapshot boundary. A tenant/user-scoped cursor in Dexie is advanced only after all participating store pulls succeed.
- Grade/Attendance pulls use an opt-in scope envelope (XD-06): current actor, complete allowed student IDs, Grade semester and records are read in one server transaction. A derived scope revision mismatch forces a full snapshot, including newly granted unchanged rows. Clients retract out-of-scope read projections, preserve durable mutation intents separately, reject stale-session/older in-flight responses and await ordered encrypted cache persistence before reporting pull success. Legacy v1 Grade/Attendance caches are discarded on migration; the queue is not. This is reconnect-time retraction, not remote erasure of disconnected devices or a universal record-deletion/tombstone protocol.
- Students and classes page by stable `(updated_at,id)` order inside a bounded window and return soft-delete tombstones during incremental pulls. Full pull remains the bootstrap and empty-cache repair path.
- `navigator.locks` coordinates tabs when supported; the expiring localStorage lease is the compatibility fallback. Neither replaces server idempotency, tenant scope, version checks, or transaction boundaries.
- Mỗi logical request/sync flow capture document-local owner một lần. Retry giữ owner gốc; successful server result được mã hóa và journal vào chính queue row của owner đó trước local apply/remap/conflict handling. Nếu account đổi giữa chừng, kết quả A có thể được giữ để A reconcile sau nhưng không được mutate live state hoặc namespace của B; committed receipt tránh resend mù một mutation server đã nhận.
- `exam_sessions.variant_manifests` is the immutable source for generated A–H question/option permutations. The server generator materializes each version and locks answer-key mutation; clients only render/print a non-A question document when that exact manifest exists.
- Exam import, scan, paper, batch, analytics, variants, and guided-grade surfaces are separate lazy chunks beneath `ExamSessionView`. SheetJS remains on-demand through `xlsxLoader`; the PWA manifest excludes `xlsx-*.js` from install-time precache and the existing static-resource route caches it after first use.
- Virtualization and OMR Worker/adaptive-threshold work are not architecture defaults. They require view/device traces and the ADR-060/068/069 corpus gates before selection.

## 6. Question Bank to Smart Exam Boundary (ADR-096)

`QuestionBankView → /api/question-bank → questionBankService` is the authoring and blueprint path. The service owns lifecycle, immutable versions, tenant scope, deterministic selection and one transaction that checks class assignment, reads active/current bank versions and materializes a normal `exam_sessions` record. Build commands carry a client-stable `buildCommandId`; the service derives a stable seed when absent and persists a canonical request hash with the session, so response-loss retry returns the same materialization while key reuse with different input conflicts. Every create/revise/import/blueprint path validates optional `branch_id` against the same tenant inside its write transaction. `examQuestionSnapshots` binds every session position to the exact bank version and content hash; grading, variants, OMR and finalization continue through existing Exam services.

The dependency direction is one-way: Question Bank may create an Exam, but an Exam never reads mutable current bank content while rendering or scoring. Blueprint shortage and unsupported materialization types fail before session insert. Authoring/build are online-only; no new client sync entity or second scoring authority is introduced.

Branch/class selection reuses the existing class catalog without coupling reusable content to a year-specific roster row: UI class IDs are transient and map to persisted `branch_id + curriculum_level=class.name`. Direct `.xlsx|.xls|.csv|.docx` imports are parsed and previewed client-side; only normalized question JSON crosses the API boundary. `POST /questions/import` validates the whole batch and tenant branch references, then writes draft items, immutable versions and audit metadata in one database transaction.

SheetJS and pinned Mammoth are lazy document chunks excluded from PWA install-time precache. Import is capped at 5 MB/50 parsed questions per file; server batch capacity is 100 normalized items. This is an authoring convenience only: it cannot activate questions, bypass lifecycle/RBAC, introduce a second file-storage path or change Smart Exam/OMR authority.

## 7. Task & Event Operations Boundary (ADR-110)

Operations is an online-first write module inside the modular monolith. `operation_events` is the only event command aggregate; `parish_events` is its minimal public calendar read projection for `PUBLIC_SUMMARY` events and has no direct UI/API writer. The write path is route validation/IANA timezone validation/UTC instant canonicalization → resource-scoped authorization → transaction → OCC/idempotency receipt + audit → response. Authorization composes account baseline, explicit active `parish_service_terms.position_code` constrained to a compatible organization unit, and resource roles; display titles and frontend visibility never grant authority. `BRANCH_LEADER` and `COMMITTEE_LEADER` are peer capabilities with separate unit scopes and can coexist as two terms for one person. Date-only service-term authority uses the server-owned deployment parish timezone, while event-derived civil dates use each event timezone. Organizer/workstream-local management cannot move an aggregate to a new organizational scope without destination-scope authority. Multiple resource IDs must resolve to one persisted event/workstream/task graph before their roles can be combined. Private list authorization uses one actor snapshot over already-loaded resource graphs and paginated responses, rather than a per-row authorization query loop.

Workstreams, memberships, tasks, assignment/dispatch rows, checklist, dependencies, participants, comments and reminders remain private Operations data. DRAFT is creator/admin-only and has no calendar/notification projection; PLANNING activates visibility and any scheduled primary invitations. OWNER dispatch stores one primary, optional reserve, acknowledgement deadline and a 70% reserve-invite instant; a target-specific inbox plus transaction/CAS acceptance creates exactly one accepted OWNER, while terminal state closes open invitations. Required readiness is derived rather than materialized, counts only active actionable staff, and is rechecked for manual READY/LIVE; cancellation does not satisfy a required task, rejected approval cannot complete a task, and cancellation reasons have a database backstop. Event lifecycle is adjacent and auditable with persistent automation pause after rewind. Multi-instance workers use transaction/CAS to auto-LIVE/COMPLETED at event instants; auto completion records unfinished counts without changing task/checklist state. Event fields lock at LIVE, terminal tasks reject structure/assignment/approval mutation, and closed events reject new planning children. Reminder production atomically persists a deterministic row into the existing notification table after current resource/recipient reauthorization; terminal resources are suppressed and external content is generic. Missing/ambiguous queue ownership is not automatically replayed. Linked event completion owns one Parish Memory `ACTIVITY` through `completion_record_id`, avoiding duplicates across reopen/recomplete. The client may keep an encrypted exact-tenant/user server-confirmed overview projection, but never cached permissions or durable Operations writes. Receipt-response compaction keeps key/hash tombstones so old retries cannot execute twice. No second calendar writer, notification system, workflow engine, generic grant table or offline sync engine is introduced.
